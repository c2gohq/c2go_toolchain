> **Release candidate:** this build is for evaluation and compatibility testing.
> It is unsigned and not production-ready.

C2Go Toolchain `v0.20260804.0-rc.1` replaces per-generated-package future-Go
version cutoffs with a centralized, compile-time toolchain contract provider.
It supports Go 1.25.x and Go 1.26.x without regenerating schema-v2 target
libraries.

[简体中文 release notes](https://github.com/c2gohq/c2go_toolchain/blob/v0.20260804.0-rc.1/RELEASE_NOTES/v0.20260804.0-rc.1.zh-CN.md)

## Changes from v0.20260802.0-rc.1

- c2go-clang now emits manifest schema v2 with two independent compatibility
  axes: `c2go_abi_epoch` and `go_toolchain_contract_epoch`.
- Schema-v2 manifests retain a minimum Go version and an informational
  validation snapshot, but no longer impose a per-artifact future-Go build
  cutoff.
- c2go-lto rejects mixed manifest generations and mismatched contracts, and
  conservatively intersects validation snapshots across translation units.
- c2go-bind preserves the released schema-v1 hard version window while
  generating minimum-only build tags and a dual-epoch compile-time anchor for
  schema v2.
- c2go-libc now carries the dependency-free `c2goabi` provider. Go 1.25.x and
  Go 1.26.x map to Go toolchain contract epoch 1; Go 1.27 and later fail closed
  until a newer provider validates them.
- Compatible future Go minor releases require only a c2go-libc provider update.
  Existing schema-v2 `.go` and `.s` target artifacts remain unchanged.
- The release workflow tests c2go-bind/goprobe and c2go-libc with Go 1.26 on
  every native target runner, then runs the packaged SDK smoke test under both
  Go 1.25 and Go 1.26 before upload.

Legacy schema-v1 libraries keep their original `max_go_version` behavior. They
must be regenerated once to adopt the provider-based model; the migration does
not silently reinterpret frozen artifacts.

## Validation before tagging

- c2go-clang and c2go-lto rebuilt successfully; the five focused schema,
  multi-TU, and archive contract tests passed.
- c2go-bind tests and vet passed under Go 1.25.9 and Go 1.26.0, including the
  structural Go frame-accounting probe.
- c2go-libc root, `dl`, and `selftest` packages passed natively on Darwin arm64
  under Go 1.25.9 and Go 1.26.0.
- Linux amd64, Linux arm64, and Windows amd64 c2go-libc packages cross-compiled
  under Go 1.26.0.
- The schema-v2 SQLite consumer passed independently under Go 1.25.9 and Go
  1.26.0 with `GOGC=1` and `GODEBUG=invalidptr=1` on the Go 1.26 run.
- Go 1.27rc1 was rejected by the centralized provider as intended; the explicit
  unverified-toolchain test override selected epoch 1 successfully.
- No generated c2go-libc or SQLite assembly changed for this version-policy
  migration.

The tagged release workflow repeats native validation on all four supported
release targets. A queued workflow is not evidence that the binary assets have
finished publishing.

## Known limitations and licensing

- C only; C++ and 32-bit targets are not supported.
- Go 1.25.x and Go 1.26.x are supported; Windows has a smaller POSIX surface.
- C2Go cannot promote an escaping C stack local to the heap. Run the standalone
  `c2go-lto` escape audit as a separate release gate.
- Interfaces and ABI details remain pre-1.0 and may change.

This aggregate contains multiple license boundaries. Preserve and review the
root and `licenses/` records before use or redistribution. A commercial
agreement cannot relicense LLVM, musl, or other third-party code.
