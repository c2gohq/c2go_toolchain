> **候选版本：**本版本用于评估和兼容性测试，尚未签名，也未达到生产可用状态。

C2Go Toolchain `v0.20260801.0-rc.1` 将 LLVM bitcode object 确立为常规多文件
构建边界，并由 Clang manifest 唯一负责 Go package import path。

[English release notes](https://github.com/c2gohq/c2go_toolchain/blob/v0.20260801.0-rc.1/RELEASE_NOTES/v0.20260801.0-rc.1.md)

## 相比 v0.20260729.0-rc.5 的变化

- `c2go-clang -fc2go -c source.c -o source.o` 现在默认把 LLVM bitcode 写入指定
  的 `.o` 路径；正常构建既不需要 `-emit-llvm`，也不需要 `-flto`。
- `c2go-lto` 可以作为 `ar` 替代：`c2go-lto rcs libname.a one.o two.o`
  会链接 bitcode 输入，并写出供 `c2go-bind` 使用的 Plan 9 汇编和 manifest 成员。
- `-flto` 与 `-flto=thin` 继续作为构建系统兼容参数接受，但不构成另一套 C2Go
  构建模式。
- `-fc2go-package=<import-path>` 现在是权威 package identity。同包
  `c2go_linkname` 目标会变成本包符号；跨包目标继续保留完整 Go linker identity。
- `c2go-bind` 不再接受重复的 `--pkg` 覆盖参数。它从 manifest 读取 import path；
  当 Go `package` 名与 import path 末段不同时，仍可使用 `--pkgname`。
- c2go-libc 已为五个支持的目标输出重新生成汇编，使用本包调用和更新后的绑定流程。
- 调试元数据会保留到独立逃逸审计和可选 bitcode 输出完成后，并仅在 Plan 9 汇编
  生成前移除，以避开不受支持的 DWARF streamer 路径。

## 常规多文件流程

```sh
c2go-clang --target="$C2GO_TARGET" -std=c2go23 -fc2go \
  -fc2go-package=example.com/acme/mypkg -O2 -c one.c -o one.o
c2go-clang --target="$C2GO_TARGET" -std=c2go23 -fc2go \
  -fc2go-package=example.com/acme/mypkg -O2 -c two.c -o two.o
c2go-lto rcs libmypkg.a one.o two.o
c2go-bind --out=./mypkg libmypkg.a
```

上面的 `.o` 虽然沿用传统 object 后缀，实际内容是 LLVM bitcode；不要把它们交给
原生系统 linker 或原生 `ar`。

## 已知限制与许可证

- 仅支持 C，不支持 C++ 和 32 位目标。
- 仅支持 Go 1.25.x；Windows 的 POSIX 接口范围较小。
- C2Go 无法像 Go 编译器一样把发生逃逸的 C 栈局部变量提升到堆上；发布前必须把
  独立 `c2go-lto` 逃逸审计作为单独门禁。
- 接口和 ABI 细节仍处于 pre-1.0 阶段，后续可能修改。

本聚合包包含多个许可证边界。使用或再分发前必须保留并阅读根目录和
`licenses/` 中的授权记录。商业协议不能重新许可 LLVM、musl 或其他第三方代码。
